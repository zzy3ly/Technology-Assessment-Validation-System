# 统一故障恢复实验 v1

日期：2026-10-13。脚本 `benchmarks/run_recovery_ab.py`；数据及逐条证据 `test_outputs/recovery_ab_v1/`。本轮只新增实验文件，没有修改恢复实现来改善分数。

## 设计与范围

18 类场景 × 3 种工作负载（求和、去重排序、加权求和），共 54 条。每条执行读取本地输入、转换、写出结果三个节点；节点内调用有明确名称与参数的本地工具。运行原版和当前版真实 Planner 控制流；通过统一替身提供固定计划和节点执行逻辑。当前版实际写入、读取原子 checkpoint；模拟中断时丢弃 Planner 对象，重建对象后恢复。未启动真实 LLM、网络服务或收费工具。

场景在首次执行前固定，没有按结果删案例或调整比例：

| 分层 | 场景 | 数量 |
|---|---|---:|
| 正常对照 | 无故障 | 3 |
| 短暂故障 | 单次超时、单次 429、单次空返回、单次执行失败、节点内第二工具超时 | 15 |
| 预算边界 | 连续两次超时，第三次才可能成功 | 3 |
| 持续故障 | 持续 429、文件缺失、参数错误、来源冲突、非法 JSON、上下文超限、权限错误 | 21 |
| 中断 | 第一个节点落盘后、第二个节点落盘后、工具成功但结果尚未落盘 | 9 |
| 语义负对照 | 返回成功但数值错误 | 3 |

选择持续故障是为了检查系统是否诚实地停止，以及避免只测“一重试就好”的案例。3 种工作负载不是 3 倍独立故障类型，不据此宣称统计显著性。这是等权场景覆盖，不代表线上故障频率，也未设目标分数。

三组对照：旧版；新版断点恢复；新版遇中断整任务重启。第三组只改变中断后的入口，保留新版重试策略，用于隔离 checkpoint 收益。所有组中断后最多重启一次，计划更新固定 NO_UPDATE；新版保持一次节点重试，退避等待设零。持续参数错误不会因为收到修复 Prompt 就自动变好，持续上下文超限也不会假设模型已经压缩上下文。

## 计分标准

恢复成功率 = 最终产物正确的故障任务数 / 48 条故障任务。排除 3 条正常对照和 3 条语义对照；持续故障也保留在分母。错误停止不计成功。

工具身份由工具名与规范化参数确定，仅在同一任务内比较：

- 重复调用：此前出现过相同身份的调用，包含必要重试。
- 成功后重复调用：相同调用此前已有成功结果；在本实验输入不变的条件下可视为可避免的重复工作。
- 失败后再次调用：重复调用减去成功后重复调用；不全部等于有效重试，持续错误的重复尝试也包含其中。
- 成功后重复调用率：成功后重复调用数 / 全部工具调用数。

工具结果通过实际产物独立判分。工具级成功仅表示执行成功，不保证业务内容正确；负对照用于保留这个区别。

## 结果

| 指标 | 旧版 | 新版断点恢复 | 新版整任务重启 |
|---|---:|---:|---:|
| 故障恢复 | 9/48 | 24/48 | 24/48 |
| 故障恢复率 | 18.75% | 50.00% | 50.00% |
| 全部任务成功 | 12/54 | 27/54 | 27/54 |
| 总工具调用 | 141 | 180 | 192 |
| 所有重复调用 | 15 | 39 | 51 |
| 失败后再次调用 | 0 | 33 | 33 |
| 成功后重复调用 | 15 | 6 | 18 |
| 成功后重复调用率 | 10.64% | 3.33% | 9.38% |

新版相对旧版恢复率提升 31.25 个百分点；但总调用从 141 增至 180，因为新版尝试恢复并完成更多任务。不能宣传为“总工具调用下降”。成功后重复调用从 15 降到 6，减少 60%，但新旧任务完成率不同，不宜单独当成成本结论。

更公平的 checkpoint 对照是两组新版：任务完成数相同，成功后重复调用从 18 降到 6，减少 66.67%；总调用从 192 降到 180，减少 12 次（6.25%）。这是整套测试集上的数字，不是实际 token 或费用节省比例。

## 分场景解释

- 短暂故障：新版 15/15 恢复，旧版 0/15。只代表这五类固定规则下的本地工具故障。
- 连续两次超时：新版 0/3，达到节点重试上限后未完成。
- 持续故障：新版 0/21，不能把失败处理正常当作任务成功。
- 中断：三组均 9/9 最终成功；旧版和新版整任务重启会重复执行前序节点，新版断点恢复复用已保存结果。
- 语义错误：三组均 0/3 正确，故障恢复机制不能保证业务正确性。

新版的 6 次成功后重复调用分别来自两个真实边界：

1. 节点内先读参考信息，再调用转换工具；转换超时导致整个节点重跑，参考信息被重复读取，共 3 次。当前缓存粒度是节点，不是节点内工具。
2. 转换工具已成功但节点结果尚未写入 checkpoint 时中断；恢复后转换工具重跑，共 3 次。当前系统不提供工具副作用与 checkpoint 的原子事务，也不保证 exactly-once。

## 可复现性与限制

```powershell
.\.venv\Scripts\python.exe benchmarks/run_recovery_ab.py
.\.venv\Scripts\python.exe -m unittest tests.test_recovery_benchmark tests.test_recovery tests.test_checkpoint -v
```

`dataset.json` 保存固定输入、场景分层和预设期望；三个模式的 JSON 保存源码路径和 Planner SHA-256、每次工具参数与结果、checkpoint 快照、状态机轨迹；`summary.json` 保存总计和分场景计数。

这是恢复机制的确定性开发集，不是盲测、真实 API 成功率或生产 SLO。非法 JSON、上下文溢出在这里作为节点错误上报，未测试真实模型生成/压缩；fallback 外部服务、模型降级、真实参数自动修复、成功重规划均未覆盖。中断通过 BaseException 模拟并重建 Planner，未执行操作系统进程强杀，不证明跨进程全栈恢复。没有测量真实退避耗时、token 成本或付费节省。

建议简历表述：**针对 18 类场景构建 54 条确定性恢复测试，48 条故障任务恢复率达 50%；相较相同新版的整任务重启策略，checkpoint 在保持完成数不变时减少 12 次工具调用（6.25%），成功后重复调用由 18 次降至 6 次。** 保留测试范围，不泛化为线上收益。
